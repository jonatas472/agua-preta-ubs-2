## 1. Contexto e objetivo

Analise o projeto existente Água Preta UBS e execute a parte da P4 correspondente à entidade Serviço, respeitando o PRD, a arquitetura atual e as instruções do repositório.

A P4 solicita a criação das entidades Room, dos DAOs, da interface Retrofit, dos ViewModels e a integração entre essas partes, além da definição de um padrão de branches e mensagens de commit.

Nesta etapa, implemente exclusivamente a parte de Serviço pela qual Isi é responsável. As demais entidades e funcionalidades dos outros integrantes não devem ser implementadas ou modificadas.

O objetivo é estruturar os serviços e horários oferecidos pela UBS, disponibilizar esses dados por meio do Room quando necessário e conectá-los à funcionalidade existente de consulta de serviços.

## 2. Etapa 1 — Análise obrigatória do projeto

Antes de alterar qualquer arquivo:

1. Leia o PRD vigente e localize a definição da entidade Serviço.
2. Consulte AGENTS.md e a documentação relevante.
3. Analise a estrutura atual do código Kotlin e identifique o pacote correto.
4. Confira a configuração do Room, incluindo entidades, DAOs e banco de dados.
5. Verifique se ServicoEntity.kt, ServicoDao.kt ou implementações equivalentes já existem.
6. Identifique a tela de Serviços e Horários e a forma como os dados são apresentados.
7. Verifique se já existem dados locais, listas fixas ou outra fonte de serviços.
8. Examine git status, o histórico recente e o diff para preservar alterações locais.
9. Confira as configurações do Gradle sem modificá-las desnecessariamente.

Depois da análise, apresente um plano de execução com os arquivos que pretende criar ou alterar, justificando cada alteração.

Não duplique classes nem substitua implementações funcionais sem necessidade.

Se houver divergência entre o PRD e a interface atual, registre a dúvida antes de alterar o comportamento do aplicativo.

## 3. Etapa 2 — Implementar ServicoEntity

Crie ou complete ServicoEntity.kt no pacote apropriado.

A definição anteriormente considerada para Serviço contém:

- id
- nome
- descricao
- horario

Confirme no PRD vigente os tipos dos campos, a chave primária e as regras de nomenclatura antes de implementar.

Requisitos:

- Utilizar @Entity do Room.
- Definir a chave primária com @PrimaryKey, respeitando o padrão do projeto.
- Utilizar os imports corretos.
- Seguir o padrão de nomes das outras entidades.
- Manter o código simples e legível.
- Incluir os comentários de identificação de responsabilidade exigidos pelo repositório, se aplicáveis.

Não invente campos, relacionamentos ou regras de negócio.

Não acrescente informações sobre serviços que não estejam definidas na documentação ou aprovadas pelo grupo.

## 4. Etapa 3 — Criar ou completar ServicoDao

Verifique se já existe um DAO para Serviço.

Caso não exista, implemente ServicoDao.kt com as operações necessárias para a funcionalidade prevista.

As operações poderão incluir:

- Listar os serviços disponíveis.
- Consultar um serviço específico.
- Buscar serviços por nome, se houver necessidade documentada.
- Inserir ou atualizar dados somente se isso fizer parte da estratégia de armazenamento definida.

Utilize as anotações apropriadas do Room, como @Dao, @Query, @Insert e @Update.

Considere Flow para consultas que precisem atualizar a interface automaticamente e suspend para operações de escrita, conforme os padrões existentes.

Confira se as consultas SQL utilizam corretamente o nome da tabela e os campos da entidade.

Não crie operações desnecessárias.

## 5. Etapa 4 — Integrar Serviço ao banco Room

Analise a classe de banco de dados existente.

Se Serviço ainda não estiver integrado, registre a entidade e disponibilize seu DAO.

Verifique:

- Se ServicoEntity está registrada nas entidades do banco.
- Se ServicoDao está declarado corretamente.
- Se existe um método para obter o DAO.
- Se a instância do banco é compartilhada conforme a arquitetura existente.
- Se a alteração exige uma migração de banco de dados.

Não crie uma segunda classe RoomDatabase.

Não altere versões ou migrações sem necessidade comprovada. Se houver uma alteração estrutural indispensável, explique o motivo e implemente somente o necessário.

## 6. Etapa 5 — Definir como os serviços serão disponibilizados

Criar uma entidade não significa que o aplicativo já terá serviços cadastrados.

Analise como os serviços e horários devem ser fornecidos segundo o PRD e a implementação atual.

Se os dados forem fixos, verifique se o projeto já possui uma lista local ou uma estratégia documentada de inicialização.

Se os dados precisarem ser armazenados no Room, identifique como serão inseridos inicialmente, sem inventar serviços ou horários.

Não crie uma tela administrativa ou um sistema de cadastro de serviços sem previsão no escopo.

Se não houver uma fonte definida para preencher a tabela, registre a pendência no relatório em vez de apresentar uma lista vazia como se a funcionalidade estivesse concluída.

## 7. Etapa 6 — Criar ou completar o ViewModel de Serviço

Verifique se já existe um ViewModel para a tela de Serviços e Horários.

Caso seja necessário criar ou completar essa camada, implemente apenas a lógica mínima para disponibilizar os dados à interface Compose.

O fluxo esperado, quando houver dados armazenados no Room, é:

1. A tela solicita a lista de serviços.
2. O ViewModel consulta o DAO.
3. Os dados são disponibilizados à interface.
4. A tela apresenta os nomes, as descrições e os horários disponíveis.
5. Estados de carregamento, lista vazia e erro são tratados adequadamente.

Utilize Flow, StateFlow e Coroutines quando necessário e compatível com o projeto.

Mantenha as consultas ao banco fora da interface.

Não implemente funcionalidades de Cadastro, Agendamento ou Vacina.

## 8. Etapa 7 — Avaliar a integração com Retrofit

A P4 menciona uma interface Retrofit, mas esta etapa deve permanecer focada em Serviço.

O PRD anteriormente definido prioriza o armazenamento local e não especifica uma API real para obter serviços da UBS.

Portanto:

- Não invente URLs.
- Não crie endpoints fictícios.
- Não presuma que existe um servidor da UBS.
- Não implemente sincronização em nuvem sem autorização.
- Não crie uma interface Retrofit exclusiva para Serviço sem necessidade documentada.

Se o professor exigir uma API real, identifique a fonte, os endpoints e o formato dos dados antes de implementar a comunicação.

Se a API não estiver definida, registre a pendência sem simular uma integração funcional.
